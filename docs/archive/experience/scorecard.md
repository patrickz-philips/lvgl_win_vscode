# Scorecard 模板

所有 review（`plan-pre-review`、`slice-review`、`feature-review`、`analyzer-review`、`human-review`）都使用本模板。

- 机器 review：填好后**追加**到 `docs/work/<feature-id>/scorecards.md`（临时，handoff 时并入归档并删除）。
- 人类 review：编排者在 chat 中完整贴出下面 §3 的模板给人类填写。

## 1. 评分维度

每项 0-5 分，总分 30。

| # | 维度 | 0-1 | 2-3 | 4-5 |
| --- | --- | --- | --- | --- |
| D1 | Spec 一致性 | 明显偏离或漏做 In scope | 主体符合，细节有偏差 | 逐条对得上，含边界与失败态 |
| D2 | 正确性 | 有 Blocker 缺陷 | 有 Major 缺陷 | 未发现缺陷，边界处理正确 |
| D3 | 验证充分性 | 无证据或伪造证据 | 跑了但覆盖不足 | 真实命令+输出，覆盖验收标准与边界 |
| D4 | 简洁性（反过度设计） | 明显过度设计/重复造轮子 | 有可删减的抽象或死代码 | 最短可行实现，优先复用与标准库 |
| D5 | 安全与边界 | 存在 OWASP 类风险或数据丢失风险 | 信任边界校验不完整 | 输入校验、错误处理、权限均到位 |
| D6 | 一致性与可维护 | 与既有代码风格/结构冲突 | 局部不一致 | 复用既有模式，命名与结构一致 |

## 2. 通过判定

同时满足才算 **PASS**：

- 总分 ≥ 24 / 30
- 任一维度 ≥ 3
- Blocker 数 = 0
- Major 数 = 0（`plan-pre-review` 阶段允许 Major ≤ 1 且已在「必须修复项」中给出明确修法）

任一条不满足 → **FAIL**，必须填写「必须修复项」和「Experience 候选」。

## 3. 模板（复制填写）

```markdown
## Scorecard: <阶段> / <feature-id> [/ <slice-id>]

- 评审人：<reviewer | analyzer | human:姓名>
- 日期：<YYYY-MM-DD>
- 评审对象：<plan.md | slice S2 的 diff | 全功能 | ...>
- 第几次：<attempts>
- 选用 skill：<运行时选了哪些 + 一句话理由；没选也写理由。人类 review 可留空>

### 评分
| 维度 | 分数 | 依据 |
| --- | --- | --- |
| D1 Spec 一致性 | /5 | |
| D2 正确性 | /5 | |
| D3 验证充分性 | /5 | |
| D4 简洁性 | /5 | |
| D5 安全与边界 | /5 | |
| D6 一致性与可维护 | /5 | |
| **总分** | **/30** | |

### 结论
**PASS / FAIL** — <一句话理由>

### Bug 清单
| ID | 严重度 | 位置 | 现象 | 期望 |
| --- | --- | --- | --- | --- |
| B1 | Blocker/Major/Minor | `projects/battery_monitor/src/battery_monitor_view.c:12` | | |

> 严重度定义：Blocker = 功能不可用/数据错误/安全漏洞；Major = 主路径行为不符 spec；Minor = 风格、命名、可读性、非关键边界。

### 理解差异（Understanding Gaps）
| ID | Spec 原文 | 实现/计划的理解 | 差异影响 | 裁决 |
| --- | --- | --- | --- | --- |
| G1 | | | | 改实现 / 改 spec / 接受 |

### 验证证据核对
| 声称的验证 | 实际命令 | 输出摘要 | 是否可信 |
| --- | --- | --- | --- |

### 未覆盖的验收标准
- <spec 中哪几条 AC 没有对应验证；无则写「无」>

### 风险与技术债
- <已知限制、`ponytail:` 标记、后续需要处理的点；无则写「无」>

### 必须修复项（FAIL 时必填，按优先级排序）
1. <可执行的动作，指明文件与做法>
2. ...

### 交回给
<analyzer | executor>，回退到阶段 `<stage>`

### Experience 候选
- **[<阶段>] <一句话教训>**
  - 现象：
  - 根因：
  - 下次：
```

## 4. 人类 review 附加项

人类 review 时，编排者除模板外还要在 chat 中提供：

- 本次功能的变更摘要与 `git diff --stat`
- 所有切片的验证命令与真实输出摘要
- 机器 review 的历史 scorecard 结论（阶段 / 分数 / 结论）
- 已知风险与 `ponytail:` 技术债清单

人类可以只填「结论 + 必须修复项」，其余留空。**人类未回复前工作流必须停住。**
